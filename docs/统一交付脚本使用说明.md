## 用户操作

双击项目根目录“交付菜单.bat”，或运行 npm run deliver。

菜单提供：
1. 仅提交推送。
2. 提交推送并打包，安装包保留本地。
3. 完整发布：提交推送、打包校验、上传草稿、远端完整字节核验、公开发布。
4. 记录已完成的审核。

首次先完成代码审核与验证，再选择第4项。提供一个JSON文件清单（如 ["backend/connections/service.js","frontend/src/hooks/useRejectedModelRefresh.ts"]），填写审核人及测试/审核证据位置。必须包含本次所有依赖改动；脚本不会自动发现遗漏的业务依赖，也不会代替人工审核。生成的审核记录保存到Git内部的nova-delivery目录，不进入产品安装包。

选择1至3，粘贴审核记录路径、输入提交说明。打包还需版本号和发布类型；完整发布还需发布说明文件。显示具体清单后输入YES一次，执行至所选终点。Git认证提示由Git自身处理。

当前通常选择GitHub测试版：沿用独立应用身份和nova-test.yml，未签名。正式签名版沿用原签名和验收门槛，未满足时会明确失败，不能用测试模式冒充正式版。

## 命令行

以下VERSION替换为实际新版本，不要照抄；不带--execute只预览，不访问远端、不提交、不构建。

    npm run deliver -- review --files files.json --reviewer "审核人" --evidence "审核记录位置及验证结果"
    npm run deliver -- run --review "审核记录路径" --mode push --message "本次提交说明"
    npm run deliver -- run --review "审核记录路径" --mode push --message "本次提交说明" --execute
    npm run deliver -- run --review "审核记录路径" --mode build --profile github-test --version VERSION --message "本次提交说明" --execute
    npm run deliver -- run --review "审核记录路径" --mode publish --profile github-test --version VERSION --message "本次提交说明" --notes-file notes.txt --execute
    npm run deliver -- status --review "审核记录路径"

完整发布需要操作者在当前进程提供NOVA_RELEASE_TOKEN；仅推送使用Git现有认证，不要求发布Token。不要把Token写入清单、发布说明或命令参数。脚本不读取客户端生成Key。

## 审核、源码与工作区

审核绑定项目、分支、起始提交及逐文件SHA256，包括新增和删除。文件修改后应重新审核并生成新记录。未列入清单的工作区改动保留；执行开始前若暂存区非空则停止，要求先整理，避免覆盖其他人的暂存内容。

提交使用独立Git索引，仅收录清单文件，保留Git提交钩子；提交树与审核构造的树不一致时停止。提交成功后仅同步这些文件的主索引。远端origin必须指向hanjiyou/nova-video-studio，远端分支必须等于审核起点或本轮提交，不自动合并、强推或推送此前未审核的本地提交。

打包从该提交克隆至独立临时目录，分别在根目录、frontend和backend执行npm ci，再调用已有Windows构建和校验脚本。首次会安装依赖，要求Windows、可用的Node/npm、Git和依赖下载网络。构建包嵌入已提交源码编号；后续发布再次校验包与源码绑定。单纯推送不要求版本号；新打包版本必须高于远端现有稳定版本。

旧desktop-release工作流改为仅手动构建并保存Actions产物，不再响应标签或写GitHub Release。统一入口发布前还检查所构建提交中的该工作流，避免遗漏工作流改动后触发重复发布。这是开发交付脚本，不改变客户端更新界面和安装过程。

## 中断与续跑

继续使用同一审核记录和相同参数执行；也可以把push提升到build，再提升到publish，不重复已有步骤。版本、发布类型及已记录发布说明不能中途更换；要交付新代码需新的审核记录。

- 提交成功但推送失败：保留提交，恢复后只推送。
- 构建失败：保留构建目录和构建日志，下一次重试构建；成功完整目录先校验而非覆盖。
- 上传中断：保留草稿，记录Release ID；请求回执丢失时按同版本查找，确认相同源码及资产后补传缺失文件；失败的单文件从头上传，不支持字节断点续传。
- 发布回执丢失：查询既有Release并重新核验远端字节，已发布则完成，不重复公开。
- 同号资产内容不同、分支改变或提交不匹配：停止，保持原数据，不自动覆盖或回滚。

进度、失败阶段、提交编号、安装包位置与Release ID保存在Git内部nova-delivery目录；status可以查看。全流程有本地锁。若进程异常退出留下delivery.lock，先确认记录的PID不再运行，再手动删除该单个锁文件；不要删除整个状态目录。构建脚本另有构建锁，其报错会给出位置。

独立构建目录位于系统临时目录，脚本不会自动删除；需要长期交付安装包时，将校验通过的产物另行归档。不要在续跑完成前清理该目录。

## 2026-10-25 首次独立构建补修

Electron 43 安装依赖后不自动准备运行文件。统一脚本在 npm ci 后显式运行依赖包自带的 install.js，由其核对版本及下载校验，并检查 electron.exe 存在后才打包。新增缺安装器、准备失败及成功路径回归；此补修不改变源码隔离或发布门槛。

真实发布预检补修：GitHub 仓库根 API 使用无尾斜杠的规范地址；固定仓库白名单允许该精确根地址，仍拒绝相似名称仓库。新增传输层回归，模拟仓库也使用规范地址。现有 GitHub 登录凭据可由操作者在内存中取得并传入发布进程；本轮沿用前次 Git credential helper，未落盘或输出 Token。


## 2026-10-25 发布网络完善（下一次交付生效）

此节替代旧脚本固定 120 秒传输超时及重复下载行为。本次审核通过后仅提交推送脚本源码，测试和限制见[完善记录](implementation/交付网络完善记录.md)。

完整发布菜单会询问代理地址。填写本机 VPN 提供的 HTTP 代理地址；例如 http://127.0.0.1:7898 仅作示例，请使用自己的实际端口。留空沿用 NOVA_RELEASE_PROXY，输入 direct 不使用脚本显式代理。命令行 deliver 和 update:release:win 均可追加：

```text
--proxy http://127.0.0.1:7898 --transfer-timeout 1800 --idle-timeout 60
```

也可用 --direct 覆盖环境代理，不能同时传 --proxy。脚本不自动读取 HTTP_PROXY/系统代理或切换 VPN 节点；direct 不保证绕过系统 TUN。此设置只管 GitHub 发布、上传与远端校验；Git 推送、npm/Electron 下载仍使用各自网络配置。代理地址不允许携带用户名密码。

API 默认总时限 60 秒、连接 30 秒；每个大文件上传/下载总时限默认 30 分钟，无应用可观察进展默认 60 秒停止。两个可选超时参数单位为秒，范围 1–7200。每 5 秒显示累计字节、耗时、平均速度；上传的 queued 指已交给传输层，受缓冲影响，不等于 GitHub 已接收。必须有成功响应及完整字节校验才算成功。

同一次交付仅对身份及完整元数据未变的文件复用已成功的远端校验；重新启动脚本或元数据缺失/变化都重新下载。不会复用持久化的旧校验结论。

出现 starter 占位时停止并保留草稿。先核对草稿 ID、源码、文件名及确属本次失败上传，人工移除失败占位后用原审核记录续跑；不能删除 uploaded 文件、未知状态资产或已发布 Release。脚本不自动清理，也不自动重试上传。

新行为须随审核文件一起提交。独立构建目录中的发布脚本绑定对应源码，旧交付记录不会自动升级为当前工作区脚本。
