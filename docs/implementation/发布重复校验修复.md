## 问题与修复

统一交付入口在同一次发布动作中向草稿和发布阶段传入同一个 verificationCache。GitHub 新建草稿返回数值 Release ID（测试为 42），deliver 在发布阶段传入 String(uploaded.releaseId)（测试为 '42'）。checkedHash 原来直接把 ID 放入 JSON 缓存键，数值和字符串编码不同，使三项已成功完整校验的资产在发布前又下载、哈希一次。

仅在 scripts/release-windows-update.cjs 的缓存身份边界将 Release ID 改为 String(id)。不改变外部 ID 返回类型，也无需更改 scripts/deliver.cjs。仓库、源码提交、标签、资产 ID、名称、大小、状态、updated_at、digest 和预期 SHA512 仍全部参与缓存键；缺少必要元数据时仍禁止复用。首次远端完整字节校验及每阶段重新读取 Release 身份、标签与资产元数据的检查保持。

缓存仍仅存在于当前交付动作的内存 Map 中；没有持久化、跨进程缓存或新的全局缓存。未传入共享 Map 的独立 run 调用各自创建缓存。错误字节不会写入缓存。凭据来源、固定仓库、源码绑定、签名、版本和发布门槛没有改动。

## 回归证据

复用并增强 scripts/windows-release.test.cjs 中既有测试：

- 实际执行模拟 draft 创建、三资产上传及校验，确认返回数值 42；随后按 deliver 的方式向 publish 传 String(uploaded.releaseId)，共享 Map 后总 hashAsset 调用数为 3。发布阶段仍重新 GET Release 和资产列表，最终只有一次 PATCH。
- updated_at 变化使单个资产重新哈希，计数从 3 到 4；随后 digest 变化再次重新哈希，计数到 5。starter 状态在资产检查处拒绝，不增加发布 PATCH。
- 相同错误 SHA512 连续校验两次均拒绝，两次都重新哈希，Map 大小保持 0，且没有上传或发布写操作。
- 不共享 Map 的两次独立调用各校验三项资产（共 6 次）；建立暖缓存后仍拒绝源码提交或标签提交不符，不发出发布 PATCH。

测试只使用合成文件、模拟 GitHub 请求与无效测试令牌。交付测试中的提交、推送只发生于受控系统临时目录内的本地测试仓库；网络层测试只使用本地 loopback/模拟传输。没有读取真实凭据、访问真实上传接口、提交本项目、推送远端、构建真实安装包、安装应用或发布 Release。
