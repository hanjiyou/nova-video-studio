# 安装包差量更新主审记录

日期：2026-10-27。结论：U01–U03源码与定向离线范围主审通过，未提交、推送、制作正式安装包或发布。现有3.6.8不包含本轮修改。电脑A/B完整安装验收未执行。

## 修复与审核结论

1. NSIS与运行时统一appId-updater缓存身份，保留原appId、package.name、资料目录及渠道。受支持include/customHeader改写最终编译目标，未改node_modules。
2. 原生复制到固定staging后不直接相信成功；对本次源和staging比较SHA512，再发布installer.exe及最小installer-state.json。首次、覆盖、应用更新复用相同安装钩子，失败不形成可信半包。源是installer.exe本身时避免替换正在执行的源。
3. 下载前按当前身份/版本及实际完整文件哈希验证基础包。没有可信记录或不一致时直接完整下载，不扫描或搬其他渠道旧包，无需用户手动修目录。检查只服务差量优化，不修改用户资料。
4. 更新器会在下载完成但未安装时提升新索引。因此每次可信差量准备只失效本渠道根current.blockmap，再按当前app.version取得匹配索引。pending完整缓存保留；无法安全失效时也完整下载。
5. 更新页区分准备、差量尝试、真实差量、完整下载/回退及已校验缓存复用。百分比/字节来自真实阶段，COPY不算传输；零变化不冒充下载。每次尝试重置，失败/销毁后迟到回调不覆盖。
6. 诊断只增加下载模式、安全回退原因和基础包原因枚举；不记录原始错误、路径、URL或凭据。不能判定的原因保持unknown。未实现字节断点续传，也未改变发布器的远端完整校验。

## 验收限制与后续

已证明生产缓存宏和prepare逻辑可供真实更新器复用；完整安装向导、注册表、快捷方式、旧应用退出、机器A/B实际安装和远端GitHub端到端升级尚未执行。hooks实际展开编译，运行阶段只调用隔离参数化缓存核心，不冒充完整NSIS安装。缓存失败由只读/缺失源等注入，不等于真实磁盘耗尽/断电验收。

首次修复版仍可全量下载，正常安装后才建立可信基础包。真正安装验收需两个连续测试版本，并在电脑A/B分别确认正常启动、资料保持、缓存正确及网络传输字节。用户无需手动搬缓存；不擅自使用本轮开发授权覆盖用户现有安装。
